## Context

CocktailDex is a markdown LLM wiki. `scripts/wiki.py compile` deterministically regenerates
`index.md` and `tags.md` from the cards in `wiki/`; `wiki.py lint` checks consistency. The
repo root mixes **content** (`index.md`, `tags.md`, `wiki/`, `photos/`) with **operational
files** (`CLAUDE.md`, `GEMINI.md`, `scripts/`, `raw/`, `openspec/`, `.claude/`).

The owner wants the wiki published as a static website on GitHub Pages, buildable locally
first, that also exposes `llms.txt` so any external LLM can query the collection over HTTP.
The repo's remote is `c892836a/CocktailDex`, so the Pages **project** URL will be
`https://c892836a.github.io/CocktailDex/`. Node 22 (with Corepack-managed Yarn) is available locally.

Three decisions were confirmed with the owner up front: (1) LLM query = **static llms.txt**
(no backend chatbot); (2) VitePress reads content **in-place** from the repo root (no `docs/`
copy); (3) navigation is generated by **extending `wiki.py`**, not a build-time glob plugin.

## Goals / Non-Goals

**Goals:**
- Build the existing wiki markdown into a browsable static site **in-place**, with `wiki.py`
  remaining the single source of truth (the site is a view, never a fork of content).
- Emit `llms.txt` (map) + `llms-full.txt` (full text) at build time, served at site root.
- Deploy to GitHub Pages via GitHub Actions on push to `main`.
- Make everything verifiable **locally** (`yarn docs:dev` / `docs:build` / `docs:preview`)
  before any push.
- Keep CI **Node-only** — no Python in the deploy pipeline.

**Non-Goals:**
- No interactive/embedded chatbot UI (GitHub Pages is static; a backend is out of scope).
- No change to the card **schema** (frontmatter fields), the ingest/lint/query workflows, or
  the human-only fields. (Card *title headings* were normalized `## {Name}` → `# {Name}` — a
  presentation tweak, see D9 — which leaves the schema, `wiki.py` parsing, and ratings intact.)
- No content migration into a separate `docs/` folder.
- No custom domain (use the default `github.io` project URL).

## Decisions

### D1 — In-place srcDir with srcExclude (not a `docs/` copy)
Set VitePress `srcDir: '.'` (repo root) and `srcExclude` to hide operational files:
`raw/**`, `scripts/**`, `openspec/**`, `.claude/**`, `node_modules/**`, `CLAUDE.md`,
`GEMINI.md`, `README.md`, `log.md` (log/readme optional to include later).
- **Why:** `index.md`, `tags.md`, and `wiki/` are already generated/maintained at root by
  `wiki.py`. Reading them in-place means zero content divergence and zero sync step.
- **Alternative considered:** a `docs/` folder with a copy/sync of content — rejected: adds a
  sync step and a second source of truth that can drift from `wiki.py` output.

### D2 — Navigation generated by extending `wiki.py compile` (committed artifact)
Extend `compile` to write `.vitepress/sidebar.generated.json` (and optionally a nav slice)
from the parsed cards; the VitePress config `import`s that JSON. The file is **committed**,
exactly like `index.md` / `tags.md`.
- **Why:** sidebar stays in lockstep with cards/index/tags from one command; keeps CI
  Node-only (no Python at build time — it just reads the committed JSON).
- **Alternatives considered:** (a) a build-time glob plugin — rejected: adds a dependency and
  gives weaker control over grouping/order; (b) hand-written sidebar — rejected: violates the
  wiki's automation principle and rots as cards are added.

### D3 — `llms.txt` via `vitepress-plugin-llms`
Use the `vitepress-plugin-llms` Vite plugin to emit `llms.txt` and `llms-full.txt` into the
build output. Configure its `domain` to the site **origin only** — `https://c892836a.github.io`
— so links are absolute and fetchable by an external LLM. The plugin appends each page's
already-`base`-prefixed path (`/CocktailDex/…`), so setting `domain` to `…/CocktailDex` would
double the base segment (`…/CocktailDex/CocktailDex/…`); origin + base resolves to the correct
`https://c892836a.github.io/CocktailDex/…`. (Implementation note: this corrects the earlier
assumption that `domain` should include the repo path.)
- **Why:** purpose-built for VitePress, follows the llmstxt.org convention, no bespoke code.
- **Alternative considered:** a custom Node post-build script concatenating `wiki/*.md` —
  rejected as reinventing a maintained plugin, though kept as the fallback if the plugin's
  output is unsatisfactory.

### D4 — `base: '/CocktailDex/'`
A GitHub Pages **project** site is served under `/<repo>/`. Set `base` accordingly so all
asset and internal-link URLs are prefixed correctly.
- **Why:** without it, CSS/JS/links 404 on the deployed site (works in dev, breaks in prod —
  a classic trap). Verified locally via `docs:preview`, which honors `base`.

### D5 — Relative photo assets resolved by Vite's asset pipeline
Cards reference `../photos/<slug>.jpg`. From `wiki/<slug>.md` with `srcDir: '.'` this resolves
to root `photos/`, and VitePress/Vite bundles referenced images into `dist` automatically.
- **Why:** least change — cards already use this path; no need to rewrite links or duplicate
  images. **Fallback** (see risks): if relative bundling misbehaves, move/copy `photos/` into
  a VitePress `public/` dir so files are served verbatim at `/CocktailDex/photos/...`.

### D6 — `ignoreDeadLinks` tuned for excluded operational files
`index.md` links to `CLAUDE.md`, `raw/inbox/`, etc., which are `srcExclude`d. VitePress's
dead-link checker would fail the build. Configure `ignoreDeadLinks` (targeted patterns for
those operational paths) so legitimate content links are still validated.
- **Alternative considered:** rewriting those links in `wiki.py` output — possible later, but
  for now keeping `index.md` faithful to the LLM workflow and ignoring known operational links
  is lower-risk.

### D7 — Built-in local search enabled
Enable VitePress's built-in local (client-side) search.
- **Why:** free, static, helps human browsing; no external service or backend.

### D8 — Yarn via Corepack; immutable installs in CI
Use Yarn as the package manager, pinned through Corepack via the `packageManager` field in
`package.json`. Local installs use `yarn install`; CI uses `yarn install --immutable` (the
Yarn-modern equivalent of `npm ci` — fails if the lockfile would change). Commit `yarn.lock`;
never `package-lock.json`.
- **Why:** the project standardizes on Yarn; Corepack pins an exact Yarn version so local and
  CI builds match without a global Yarn install.
- **Note:** GitHub Actions enables Yarn with `corepack enable` and caches via
  `actions/setup-node` with `cache: 'yarn'`.

### D9 — Card title heading normalized to H1 (`#`)
Each card's top heading was changed from `## {Name}` to `# {Name}` (and the CLAUDE.md §3b
template). VitePress and `vitepress-plugin-llms` derive a page's title from its first H1 (or a
frontmatter `title:`); with only an H2, every page and `llms.txt` entry rendered as "Untitled".
- **Why:** a one-character, idiomatic fix (a page's title *should* be an H1) that gives both the
  human site and the `llms.txt` index proper cocktail names. It does **not** change the card
  schema — `wiki.py` reads the name from frontmatter, so `compile`/`lint` are unaffected and the
  human-only rating/variation fields are untouched.
- **Alternative considered:** adding a `title:` frontmatter field to every card — rejected as a
  redundant schema addition that merely duplicates `name:`.

## Risks / Trade-offs

- **Relative photo assets may not bundle as expected** → Mitigation: verify in `docs:build`;
  fallback to a `public/photos/` copy (D5). Low risk, fast to detect locally.
- **`base` misconfiguration ships a broken prod site that looks fine in dev** → Mitigation:
  always validate with `docs:preview` (honors `base`) before pushing; CI deploy is the final
  check at the real URL.
- **Generated sidebar drifts if owner edits cards without recompiling** → Mitigation: `compile`
  already runs as part of every ingest (CLAUDE.md §5); optionally add a CI check that
  `wiki.py compile` produces no diff. Document the dependency.
- **`vitepress-plugin-llms` API/version churn** → Mitigation: pin the version in
  `package.json`; verify `llms.txt`/`llms-full.txt` contents in the local build; custom-script
  fallback available (D3).
- **Pages not yet set to "GitHub Actions" source** → the first deploy fails. Mitigation: a
  one-time manual repo settings step, called out explicitly in tasks and migration.
- **Dead-link `ignoreDeadLinks` is broad enough to hide real broken links** → Mitigation: use
  targeted patterns for known operational paths rather than a blanket `true` where feasible.

## Migration Plan

1. **Local:** add `package.json`, `.vitepress/config`, plugin; extend `wiki.py` to emit the
   sidebar JSON; run `wiki.py compile`; `yarn install`; `yarn docs:build`; `docs:preview`.
   Verify: pages render, photos load, card↔card links work, `/llms.txt` + `/llms-full.txt`
   exist with absolute URLs, search works.
2. **CI/CD:** commit (incl. `yarn.lock` and the generated sidebar JSON); add the
   Actions workflow; push to `main`.
3. **Repo settings (one-time):** Settings → Pages → Source = **GitHub Actions**.
4. **Verify prod:** open `https://c892836a.github.io/CocktailDex/` and `…/llms.txt`.
5. **Rollback:** revert the workflow / set Pages source back to None. The wiki markdown is
   never mutated by the build, so there is **zero data risk** — rollback only removes the
   published site.
