## Context

The VitePress site (capability `vitepress-site`) builds in-place over the wiki markdown and
deploys to GitHub Pages under `/CocktailDex/`. It currently uses the **stock default theme** —
no `.vitepress/theme/` directory exists; `config.mjs` only configures nav/sidebar/search. The
content files it renders (`index.md`, `tags.md`, the sidebar JSON) are **generated by
`scripts/wiki.py compile`** and must never be hand-edited. CI is Node-only.

This change adds a *styling layer only*. The hard constraint shaping every decision: we may not
edit generated content, and we may not write or alter the human-only rating values. So all
beautification must be expressed as theme CSS + presentational components that consume the
existing rendered markup.

## Goals / Non-Goals

**Goals:**
- A cohesive amber/copper speakeasy identity with first-class light AND dark modes.
- Serif display headings + clean sans body.
- Tag hashtags rendered as dimension-coloured chips.
- Read-only star rendering of `_ / N` rating lines; polished photos, tables, and nav.
- Zero edits to generated files; CI stays Node-only.

**Non-Goals:**
- No fully custom theme (we `extends` the default — keep its layout, sidebar, search).
- No changes to `scripts/wiki.py`, card frontmatter, or the tag VOCABULARY.
- No editing of rating *values* — stars are display only; blank stays blank.
- No new build-time Python; no redesign of the home page into a `layout: home` hero (that would
  require changing the generated `index.md` — out of scope here).

## Decisions

### D1 — Extend the default theme, don't replace it
`.vitepress/theme/index.js` does `import DefaultTheme from 'vitepress/theme'`, imports
`./custom.css`, and exports `{ extends: DefaultTheme, enhanceApp, Layout }`. Keeps sidebar,
search, outline, and dark-mode toggle for free.
*Alternative rejected*: full custom theme — far more surface area, loses built-in features, no
benefit for a styling-only goal.

### D2 — Colour via CSS-variable override, both modes in one file
Override VitePress tokens in `custom.css`: `:root { … }` for light, `.dark { … }` for dark.
Key tokens: `--vp-c-brand-1/2/3`, `--vp-c-brand-soft`, `--vp-c-bg`, `--vp-c-bg-alt`,
`--vp-c-bg-soft`, `--vp-c-text-1/2`. Same hue (amber/copper) across modes; only lightness/chroma
differ (light = deep copper `#B0561E`; dark = bright gold `#E3A45C`).
*Alternative rejected*: hard-coding colours on selectors — fights the default theme's own
variable cascade and breaks the dark-mode toggle.

### D3 — Tag chips need a small global component (not pure CSS)
Pure CSS can colour all chips uniformly, but "one colour family **per dimension**" requires
mapping a tag token → its dimension. That mapping is data. We mirror the 6-dimension membership
from `scripts/wiki.py`'s VOCABULARY into a small lookup inside a global `<TagChip>` /
`<TagList>` component (or an `enhanceApp` directive). The component reads the existing `#Tag`
text and emits a coloured pill with a `data-dimension` attribute that `custom.css` styles.
*Alternative rejected*: regenerating tags.md/cards with colour classes — would touch generated
files. *Trade-off*: the dimension map is duplicated from Python; mitigated by D-Risk below.

### D4 — Star ratings rendered read-only from the existing line
A `<Rating>` component (or a markdown-it/DOM transform) parses the existing `**Eric — Rating:**
N / 5` line and renders `★` glyphs. It only *reads* the number already in the markdown; it never
writes, defaults, or infers a value. Blank (`_ / 5`) renders as an empty/"not yet rated" state,
matching the index table's `—` convention.
*Alternative rejected*: storing numeric ratings in frontmatter for richer rendering — that is a
data-model change touching cards and is out of scope; also risks implying the LLM authors ratings.

### D5 — Fonts loaded without blocking the build
Playfair Display (headings) + keep Inter (body). Prefer self-hosting via the theme assets or a
preconnect/preload in `config.mjs` `transformHead`; fall back to a CDN `<link>` if self-hosting
is heavy. Apply serif only to `h1, h2` inside the doc content via `custom.css`; leave
`--vp-font-family-base` (Inter) for everything else.
*Alternative rejected*: switching the global base font to serif — hurts body readability.

### D6 — Photo / table / nav polish is pure CSS
Card photos: target the content `img` with rounded corners, soft shadow, `max-width`, centering,
and a slight brightness reduction in `.dark`. Index table: zebra striping via `:nth-child`,
header on `--vp-c-bg-alt`, row hover. Nav: a 🍸 mark via `nav-bar-title-before` slot or
`logo`/title CSS. No markup changes.

## Risks / Trade-offs

- **[Dimension map drift between Python VOCABULARY and the JS chip component]** → Keep the JS map
  small and clearly comment it as "mirror of scripts/wiki.py VOCABULARY — keep in sync"; a chip
  whose tag isn't found falls back to a neutral default colour (never errors). Lint/visual check
  after any VOCABULARY change.
- **[Component fails to match card markup, hiding content]** → Components must degrade gracefully:
  if parsing fails, render the original markdown untouched. Never throw on unexpected input.
- **[Star rendering misread as the LLM authoring a rating]** → Stars are derived purely from the
  number already present; blank ratings render an explicit "not rated" state. Document this in the
  component. No write path exists.
- **[Web font slows first paint / fails offline]** → Use `font-display: swap` and preconnect;
  if the font fails to load, the serif stack falls back to system serif — site stays readable.
- **[Dark-mode contrast]** → Verify both palettes against WCAG AA for text on bg and brand on bg;
  adjust lightness if a token fails.

## Migration Plan

- Additive only: new files under `.vitepress/theme/`. First run that finds a `theme/` dir makes
  VitePress pick up the custom theme automatically.
- **Rollback**: delete `.vitepress/theme/` (and revert any `config.mjs` font/logo lines) → site
  reverts to the stock default theme. No content or data is affected because nothing generated was
  touched.
- Verify locally with `yarn docs:dev` / `yarn docs:build` before pushing; CI build must stay green
  with no Python step.

## Open Questions

- Self-host Playfair Display vs CDN link? (Lean self-host for offline/Pages reliability; decide at
  implementation based on asset weight.)
- Implement tag chips & stars as global components rendered in markdown, or as a post-render DOM
  transform in `enhanceApp`? Both satisfy the spec; pick whichever degrades most gracefully.
